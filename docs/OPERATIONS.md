# Status site operations

This repository owns the status page source, the status document, the build,
the generated artifact, and the validation that proves them. SBK-Techno/platform
owns the public edge: the `status.ia.sbktechno.com` Caddy site block, TLS and
DNS, response headers, cache policy, the release deploy, and rollback. The
generated README is owned by the platform; this page is the repository-owned
operational record the platform README generator links to. `AGENTS.md` is
generated from the platform template and is never edited here; its status
section must link this page at the platform source.

## One owner per fact

| Fact | Owner |
| --- | --- |
| Page templates, styles, scripts, French and English copy | this repository |
| `status.json` schema and committed seed | this repository |
| Hashed site assets, `site.manifest.json`, `asset-retention.json` | this repository build |
| Brand assets and `brand.manifest.json` | SBK-Techno/brand through the platform generator |
| Artifact file set, required names, content-hash shape | SBK-Techno/platform `scripts/deploy/status_artifact.py` |
| Caddy site block, security headers, CSP response header, cache policy | SBK-Techno/platform |
| Release deploy, atomic swap, release records, rollback | SBK-Techno/platform |
| DNS record, certificate, and Caddy reload | SBK-Techno/platform operator step |

`scripts/platform_contract.py` is the only consumer of the platform artifact
contract and naming standard. It loads the platform's artifact validator and
reads the status host and served document name from the platform projections,
so this repository does not repeat them. `scripts/artifact_build.py` produces
the exact tree that validator publishes.

## Build

```sh
make brand          # regenerate brand assets, pages, manifests, retention
make artifact       # write dist/ in the platform artifact layout
make validate       # repository gate
```

`make artifact` is the one entry point for a deployable tree. It writes the two
pages, their content-hashed site assets, the published brand assets, both
manifests, and `asset-retention.json` with the retired hashed names it still
protects. It never writes `status.json`: the publisher writes the live document
beside the release tree, so a release swap cannot replace a fresh heartbeat
with the one that was current when the artifact was built.

The build is deterministic. `scripts/build_site.py` reuses the snapshot instant
recorded in the committed page while the document digest matches, so rebuilding
an unchanged document is byte-identical. `make artifact-check` builds twice in
isolation, compares the canonical path-and-digest list, and validates both
trees with the platform contract. `dist/` is generated output and is ignored by
Git.

### Asset provenance

The brand repository's `assets.json` is the single owner of the logical web
assets. Its `assets/web/manifest.json` maps each name to a content-hashed file,
digest, media type, and byte size. This repository never copies that list:
`brand.manifest.json` is generated by the platform's `cmd/genstatus`, and
`site.manifest.json` records only the four site assets this repository builds.
Templates reference `{{asset:<name>}}` and `{{site:<name>}}`; a literal hashed
filename, an unknown name, or an unresolved placeholder fails the gate.

### Content hashes and retention

Every generated asset name carries the content hash defined by the platform
artifact contract. A changed file gets a new URL, so a cached document cannot
pair a new script with an old stylesheet. `asset-retention.json` keeps a retired
hashed name addressable for seven days, longer than a browser that has not yet
revalidated the page. `make brand` records newly retired names and deletes
entries whose window expired; `make brand-check` fails when a generated file
has no record or its record outlived the file.

### Snapshot binding

The committed page is a real snapshot, not a placeholder. At publish time the
build renders the overall state, component rows, incidents, exact
`generated_at`, and a snapshot marker from the exact `status.json` bytes. The
body records the document SHA-256 as `data-status-digest` and the instant the
freshness rules were applied as `data-snapshot-at`. The validator re-renders the
same document and rejects a page whose digest, instant, headline, rows, counts,
summary, or stale notice disagree.

A missing, empty, future, expired, or aged heartbeat forces the headline, every
row, and the vitals count to `unknown`; only a fresh heartbeat may repeat the
publisher summary. With JavaScript disabled the snapshot stays visible and the
page links `status.json`. With JavaScript enabled the snapshot stays on screen
until the first read succeeds or fails, then refreshes every 60 seconds and on
visibility change. A failed read never shows the stale notice at the same time.

## Response headers and CSP

The page carries the strict meta policy generated from `templates/csp.txt`.
The meta policy omits `frame-ancestors` because browsers ignore it there; the
platform edge owns the authoritative response CSP, HSTS, `X-Content-Type-Options`,
`Referrer-Policy`, `X-Frame-Options`, and every `Cache-Control` value. This
repository keeps no Caddyfile, header list, or cache policy. `make verify-published`
checks the live bytes, digests, content types, conditional request, and cookie
and listing behaviour; the platform's edge tests prove the headers.

## Brand and presentation

The graphite header renders the brand layer's approved `logo-reverse.svg`
unchanged at its intrinsic 284x118 ratio. Its width comes from the brand's
`--sbk-logo-header` token (112 px), so the page does not define its own header
size. This is a recorded deviation from the brand guideline's 240 px minimum:
the shared provider shell token is 112 px, and the status page follows the token
rather than inventing a client-logo exemption. Revisit it with the brand owner
before changing the asset.

The footer uses the published `icon-color.svg` on a `--sbk-text` plate. The
brand blue measures 2.92:1 directly on the `#080A0F` canvas, 5.99:1 on the
plate, and the plate separates from the canvas at 17.47:1. `cmd/genstatus`
resolves the reverse lockup and the icon from the brand manifest, rejects the
colour lockup on this surface, and fails closed when the reverse lockup is
missing.

Print and forced-colours light mode cannot use the white wordmark on a light
sheet. Both blocks hide the reverse lockup and show the one-colour mark with a
text wordmark. The print palette is generated from the brand's light tokens and
re-measured by the validator, so it cannot drift from the brand sheet.

`presentation()` in `status-model.js` is the single owner of every visible
decision and returns exactly one mode (`loading`, `fresh`, `stale`, or `error`)
and one banner. The page has no external runtime dependency, analytics, cookie,
browser storage, service worker, or beacon; `status.json` is fetched with
`credentials: "omit"` and `cache: "no-store"`.

## The header contrast exemption

The header lockup is the brand's logotype, so WCAG 1.4.11's logotype exemption
applies. The approved `#2255BC` fill measures 2.92:1 on the rendered `#080A0F`
header surface, below the 3:1 non-text threshold. No uniform surface satisfies
both elements: the blue needs a light surface where the white wordmark falls
below 2.5:1, and the white wordmark needs a dark one where the blue stays at or
below 2.92:1.

The exemption is not a blanket pass. `scripts/validate_status.py` reads the
surface from `.status-header` in `styles.css` and the fills from the file the
page references; it requires exactly `#FFFFFF` and `#2255BC`, requires the white
wordmark to reach 4.5:1, records the blue ratio against the rendered surface,
and checks that the header size comes from `--sbk-logo-header`. A recolour or a
surface change fails until the brand layer publishes a dark-surface variant and
the record is replaced by a 3:1 threshold. This repository must not recolour a
published asset.

## Deploy and DNS

The platform owns the deploy and the edge. Its `scripts/deploy/status.sh` builds the
deterministic tar from the manifests in this checkout, verifies the platform
gate attestation, stages the host installer, swaps the release in one rename,
verifies it, and restores the previous release on failure. `--rollback` is the
only rollback path. GitHub Pages is no longer an owner or a fallback: the
`CNAME`, `.nojekyll`, Caddyfile, cache policy, and Pages deployment were
removed from this repository. The DNS record points at the platform host and
the platform Caddy block serves the site. The remaining operator step is to
disable Pages for this repository and remove its custom domain, so the old
Pages build cannot answer on a stale hostname; the platform documentation owns
the exact command.

## Post-deploy check

```sh
make verify-published URL=https://status.ia.sbktechno.com/
```

This is read-only, bounded, and outside `make validate` because it needs the
live origin. It validates the live `status.json` schema and freshness, binds
the pages to the built bytes, every referenced resource to its manifest digest,
and the snapshot attributes to the committed document the page was built from.
CI is billing-blocked, so run it after the platform deploy. It does not assert
the HMAC receipt or the edge headers; local publication and the edge belong to
the platform.
