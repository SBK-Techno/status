# SBK Techno status page

Public, static service status page for `status.ia.sbktechno.com`, hosted on GitHub Pages.

## What this site is

- A static GitHub Pages site intended for `https://status.ia.sbktechno.com`, served from the repository root.
- Plain HTML, CSS, and JavaScript with no external runtime dependency: no framework, third-party font, remote image, analytics, cookie, or browser storage.
- The platform host publishes `status.json` at the site root. The publisher is pending; until it exists, the committed seed reports a stale signal. This page reads only that public file. It never calls the private platform, the portal, or the AI gateway.
- The committed HTML carries a publish-time snapshot: the overall state, the component rows, the incidents, the exact `generated_at`, and a marker saying the snapshot may no longer be current. A visitor without JavaScript sees the published status instead of a fallback that says nothing is displayed. The snapshot is bound to the exact `status.json` bytes by digest, so it cannot outlive or overstate the heartbeat it was rendered from.
- If the platform host is down, GitHub Pages still serves the page, its assets, and the last published `status.json`. The snapshot remains visible; a stale or missing heartbeat is rendered as `unknown` with a stale notice, never as a live claim.
- French is the default language. English is available with the `FR | EN` switch. The choice is kept in memory and can be shared as `?lang=en`; the page uses no browser storage.
- This is not the documentation site. Documentation is private and served by Caddy.

## Brand and shared assets

The site is an SBK-operated surface, so it uses the same web brand system as the operator portal and the private documentation. The brand repository's `assets.json` is the single owner of the logical web assets, and `assets/web/manifest.json` maps each logical name to a content-hashed file, digest, media type, and byte size. This repository never copies that brand list: `brand.manifest.json` is generated by the platform, and `site.manifest.json` records only the four site assets this repository generates.

The graphite header renders the brand layer's approved `logo-reverse.svg` unchanged, at its intrinsic 284x118 aspect ratio. Its width comes from the brand's `--sbk-logo-header` token (112 px, height auto), so the status page does not define its own header size. This is a recorded deviation from the brand guideline's 240 px minimum: the shared provider shell token is 112 px, and the status page follows the token rather than inventing a client-logo exemption. Revisit the deviation with the brand owner before changing the asset. The footer uses the published `icon-color.svg` on a `--sbk-text` plate: the brand blue measures 2.92:1 directly on the `#080A0F` canvas, 5.99:1 on the plate, and the plate separates from the canvas at 17.47:1. `cmd/genstatus` resolves the reverse lockup and the icon from the brand manifest, rejects the colour lockup on the status surface, and fails closed when the reverse lockup is missing.

### Header lockup size and contrast

The header lockup is the brand's logotype, so WCAG 1.4.11's logotype exemption applies to it. The validator records one explicit exemption: the approved `#2255BC` fill measures 2.92:1 on the rendered `#080A0F` header surface, below the 3:1 non-text threshold. No uniform surface can satisfy both elements: the blue needs a light surface (where the white wordmark falls below 2.5:1) and the white wordmark needs a dark one (where the blue stays at or below 2.92:1).

The exemption is not a blanket pass. `scripts/validate_status.py`:

- reads the surface from `.status-header` in `styles.css` and the fills from the file the page references;
- requires exactly the approved fills `#FFFFFF` and `#2255BC`, so a recolour such as `#111111` fails;
- requires the white wordmark to reach 4.5:1 and the recorded blue ratio to match the rendered surface, so a surface change fails until it is re-approved;
- verifies every published asset's SHA-256 and byte size and checks that the header size comes from `--sbk-logo-header`.

Lifting the exemption requires the brand layer to publish a dark-surface variant whose icon and `TECHNOLOGIES` label reach 3:1 while the wordmark remains legible; this repository must not recolour the published asset.

`templates/index.html` and `templates/404.html` are the source. They reference brand assets with `{{asset:<logical-name>}}` placeholders and site assets with `{{site:<logical-name>}}` placeholders. `make brand` runs `cmd/genstatus` from the platform checkout, then the site renderer and the retention gate:

- `cmd/genstatus` resolves every brand placeholder from the brand manifest and fails on an unknown name, an unresolved asset placeholder, or a literal hashed brand filename; it writes the hashed brand assets and `brand.manifest.json`.
- `scripts/build_site.py` resolves the site placeholders to content-hashed names, writes `site.manifest.json`, generates the print palette from the brand light tokens, and renders the snapshot from the exact `status.json` bytes.
- `scripts/prune_assets.py` records newly retired generated files in `asset-retention.json` and deletes files whose seven-day retention window has expired. `make brand-check` fails when an unmanifested file has no record or its window is overdue.

Never edit the root `index.html`, `404.html`, `styles.css` hashed copies, `site.manifest.json`, `asset-retention.json`, the hashed brand assets, or `brand.manifest.json` by hand. Change the template, the site source, the document, or the brand repository and run `make brand`. `make brand-check` verifies the committed output without writing. Both targets read `.toolchain/platform` and `.toolchain/brand` by default; pass `PLATFORM=` and `BRAND=` to use other checkouts.

The page links exactly one `brand.<hash>.css`. `scripts/validate_status.py` requires that link, proves its filename is the `brand.css` entry in `brand.manifest.json`, and recomputes the file's SHA-256 and byte size. A second brand link, a link to an older sheet, or a hand-edited digest fails. An unmanifested file is allowed only inside the seven-day retirement window; after that the same gate fails until `make brand` prunes it.

The platform command `cmd/brandlint` is the design gate for every SBK-operated surface. It reads `brand.manifest.json` and the brand manifest, and it rejects raw colours, literal font stacks, external stylesheet imports, missing shell markers (`data-surface="provider"`, `sbk-surface`, `sbk-header`, `sbk-footer`, and `Exploité par SBK Techno`), unresolved placeholders, digest or size drift, and a published asset that a page does not reference. Client apps are exempt.

`styles.css` contains only status-page layout. Every colour, font family, spacing value, and radius resolves through a `--sbk-*` token declared in the brand stylesheet.

## Presentation

The public board is a graphite surface (`data-theme="dark"`). It opens with a text status word in the status colour, a monospaced read time, and a compact inline-SVG vitals instrument on the right. The instrument is decorative and `aria-hidden`; its arcs and counts mirror the component board, which is the accessible source of the same facts. The component rows and the incident timeline are separated by hairlines rather than cards. The theme colour is the dark canvas token, not a second literal.

`presentation()` in `status-model.js` is the single owner of every visible decision. It returns exactly one mode: `loading`, `fresh`, `stale`, or `error`. It also returns exactly one banner: `null`, `stale`, or `error`. The renderer does not combine the payload, the error flag, and freshness by itself, so the headline, the rows, the vitals count, and the notice cannot disagree.

- `loading`: a read is in flight, for example after a retry or a language switch. The page says `L'état du service est en attente` and `Lecture de l'état publié dans status.json.` with no alert. On first load the publish-time snapshot stays on screen instead; a short bounded read window retries quietly, and the error view appears only after that window ends.
- `fresh`: the publisher's confirmed status and summary are shown. This is the only state that repeats the publisher summary.
- `stale`: a missing, empty, future, expired, or aged heartbeat shows `L'état du service est inconnu`, one plain sentence that the service is not confirmed down and the page updates when a signal arrives, `Dernier signal`, `Dernière lecture`, and the source link. The stale notice sits above the hero.
- `error`: one error notice with one retry action, no rows, no vitals, and no counts. A failed read never shows the stale notice at the same time.

The vitals instrument uses solid arcs only for confirmed component states. Unknown segments are dashed and muted, so a fully unknown board never looks like a solid healthy ring. The centre is a plain count such as `5 composantes`, never a zero-padded `05`. The legend counts the same components.

The component board is a compact list: an index, a name, and a status badge. One shared line above the list explains the state for every row. The page does not repeat the same sentence five times.

The static HTML is a real snapshot, not a placeholder. At publish time the workflow holds the exact signed document and `scripts/build_site.py` renders the headline, the component rows, the incident journal, the `generated_at` time, and a snapshot marker into the page. The body records the document's SHA-256 and the instant the freshness rules were applied. `scripts/validate_status.py` re-renders the same document and rejects a page whose digest, instant, headline, rows, counts, summary, or stale notice disagree. A stale, future, expired, or missing heartbeat forces the headline, every row, and the vitals count to `unknown`; only a fresh heartbeat may repeat the publisher's summary.

With JavaScript disabled the page keeps that snapshot, hides the language switch and the live check time, and links `status.json` in the `<noscript>` note and the footer. With JavaScript enabled, the snapshot stays on screen until the first read succeeds or fails; the page then refreshes every 60 seconds and on visibility change. A failed read replaces the board with the unavailable view and one retry action, as before.

Print and forced-colours light mode cannot use the reverse lockup: its white wordmark disappears on a light sheet. Both blocks hide that asset and show the published one-colour `icon-color.svg` with a text `SBK Techno` wordmark. The print palette is generated from the brand's light tokens and re-measured by the validator, so it cannot drift from the brand sheet.

At most one notice sits above the hero, so a failed read or an unconfirmed heartbeat is visible on the first screen at every width without two contradictory failures.

## Hosting and DNS

- GitHub Pages origin: `sbk-techno.github.io`.
- The custom domain CNAME target is `sbk-techno.github.io`. Create a DNS CNAME record for `status.ia` that points to `sbk-techno.github.io`.
- The `CNAME` file in this repository contains `status.ia.sbktechno.com` followed by one newline. GitHub Pages uses it to serve the custom domain.
- `.nojekyll` disables Jekyll processing. GitHub Pages serves the committed output as-is; the generator runs before push, not on Pages. Pages is configured to deploy from the `main` branch root.
- The custom domain is live at `https://status.ia.sbktechno.com/`; the Pages certificate is valid and HTTPS enforcement is enabled.
- `404.html` is served by GitHub Pages for unknown paths. Its links use absolute paths because a 404 response can appear at any URL.
- Enable HTTPS for the custom domain in the repository's Pages settings.

### Caching and delivery

GitHub Pages sets a short cache on every response, including HTML; it does not let this repository choose per-file headers. The site therefore treats HTML and assets differently by **URL**, not by header:

- The pages link only content-hashed copies of `styles.css`, `app.js`, `status-model.js`, and the generated print palette under `assets/`, recorded in `site.manifest.json`. The unhashed files remain build inputs and are not referenced by either document. A change produces a new URL, so a cached HTML document cannot pair a new script with an old stylesheet or vice versa.
- `index.html` and `404.html` keep stable URLs. A browser may reuse them for the Pages cache window; the hashed asset URLs make that reuse safe. The previous generated files are retained for seven days (`asset-retention.json`), longer than any Pages HTML cache.
- The status document is fetched with `cache: "no-store"` and a cache-busting query; the page polls every 60 seconds and on visibility change.

The future edge should set `Cache-Control: public, max-age=600, must-revalidate` for HTML and `public, max-age=31536000, immutable` for `assets/` and the hashed brand files. GitHub Pages cannot send those headers, and `immutable` is not safe to emulate with a meta tag. Until the edge exists, the hashed URLs are the mismatch protection.

## Heartbeat

The platform `cmd/statuspublisher` probes the public surfaces, writes `status.json` atomically, signs the exact bytes with HMAC-SHA256, and dispatches `.github/workflows/publish.yml`. The workflow verifies the signature with the `STATUS_HEARTBEAT_HMAC` repository secret and writes those exact bytes to `status.json`. It then runs `make brand` to render the snapshot from the new document and to prune assets whose retention window expired, runs the same `make validate` gate as CI, and only then commits and pushes `status.json`, `index.html`, `site.manifest.json`, `asset-retention.json`, and any changed generated assets; Pages then deploys the branch. The publisher is implemented, but the host timer and credentials must be installed before the page leaves its stale seed.

The host reads the key from `/run/secrets/status-heartbeat-hmac` and a fine-grained GitHub token with Actions write access on this repository from `/run/secrets/status-dispatch-token`. The HMAC value must equal the repository secret. Never commit either value.

The page fetches the file every 60 seconds with `cache: "no-store"` and a cache-busting query. It refreshes immediately when the tab becomes visible after being hidden, and it does not poll while hidden.

On first load the publish-time snapshot stays on screen while a bounded read window retries. The error view appears after that window ends, with one retry action. A manual retry clears the retained payload and returns to loading, so an old payload is never presented as the current read while the new one is in flight. A failed read never shows a stale notice at the same time.

Freshness rules:

- `generated_at` is null, empty, or unparseable: no heartbeat. `overall` and every component must be `unknown`; the validator rejects a document that claims a healthy state without a heartbeat.
- `generated_at` is more than 5 minutes in the future: invalid. Both the validator and the page reject the claim instead of treating the negative age as fresh.
- `expires_at` is in the past, or `generated_at` is older than 15 minutes: stale.
- Any missing, empty, future, expired, or aged heartbeat forces the headline, every component row, and the vitals signal count to `unknown`, shows no per-row verification time, and opens with the stale notice above the hero. The document's own summary is never repeated as a current claim.
- An expired or aged heartbeat still shows its `generated_at` as the last signal and snapshot time, because that timestamp is the last signal, not a current confirmation. The rows stay unknown and the notice explains why.
- A failed fetch renders the unavailable view even when a previous payload is retained: no rows, no vitals, and no counts from the old document, component and incident counts read `Indisponible`, and one error notice with one retry action sits above the hero. The check time keeps the last successful read time, or `Inconnu` before the first read; a failed attempt never moves it.

The publisher writes `generated_at` and `expires_at` in UTC. `expires_at` is at most 15 minutes after `generated_at`. The page treats the signal as stale after that window even if `expires_at` is later, so the timer must run more often than 15 minutes. Incidents stay operator-owned: the publisher copies them from its configured incident file and never invents or resolves one.

## Schema

```json
{
  "version": 1,
  "generated_at": "2026-10-24T12:00:00Z",
  "expires_at": "2026-10-24T12:15:00Z",
  "overall": "operational",
  "summary_fr": "Tous les services fonctionnent normalement.",
  "summary_en": "All services are operating normally.",
  "components": [
    {
      "id": "portal",
      "label_fr": "Portail",
      "label_en": "Portal",
      "status": "operational",
      "detail_fr": "Le portail répond.",
      "detail_en": "The portal is responding."
    }
  ],
  "incidents": [
    {
      "id": "inc_20261024_1100",
      "status": "monitoring",
      "title_fr": "Latence élevée sur le portail",
      "title_en": "Elevated latency on the portal",
      "started_at": "2026-10-24T11:00:00Z",
      "updated_at": "2026-10-24T11:30:00Z",
      "summary_fr": "Le service est stable. Nous continuons de surveiller.",
      "summary_en": "The service is stable. We continue to monitor."
    }
  ]
}
```

Required fields:

- Top level: `version`, `generated_at`, `expires_at`, `overall`, `summary_fr`, `summary_en`, `components`, `incidents`.
- Component: `id` (unique), `label_fr`, `label_en`, `status`, `detail_fr`, `detail_en`.
- Incident: `id` (unique), `status`, `title_fr`, `title_en`, `started_at`, `updated_at`, `summary_fr`, `summary_en`.
- `version` must be `1`.
- `generated_at` and `expires_at` are null or UTC ISO 8601 timestamps, and both must be null or both set. When they are null, `overall` and every component status must be `unknown`; a document cannot claim a confirmed state without a heartbeat. A heartbeat more than 5 minutes in the future is rejected. Incident timestamps are UTC ISO 8601 timestamps.
- `components` must be a non-empty list. Components are rendered in JSON order.
- Active incidents are rendered before resolved incidents. Within each group, JSON order is preserved.

## Local preview

```sh
python3 -m http.server 8000
```

Open `http://127.0.0.1:8000/`.

Do not open `index.html` through `file://`. Browsers block the `status.json` fetch for local files, so the page shows its error state.

Run the local checks with:

```sh
make validate
```

`make validate` needs the platform and brand checkouts. By default it reads `.toolchain/platform` and `.toolchain/brand`; that directory is Git-ignored, so a local checkout never becomes part of the site. Create the links once:

```sh
mkdir -p .toolchain
ln -s /path/to/platform .toolchain/platform
ln -s /path/to/brand .toolchain/brand
```

Alternatively pass `make validate PLATFORM=/path/to/platform BRAND=/path/to/brand`. CI pins both revisions in `.github/actions/toolchain/action.yml`; use the same revisions locally when reproducing a CI result. A missing checkout fails with the exact path and the override to set.

`make validate` expands `GATE_TARGETS` from the Makefile: the document and site validator, the unit suites, `brand-check` (generator check), `render-check` (rendered-site reproduction), `assets-check` (retention ledger), the platform `statuscheck` against `status.json`, and `brandlint`. The workflow checks out this repository, invokes the pinned toolchain action, and runs that one target; it keeps no second list of checks.

## Validation

`.github/workflows/validate.yml` runs on every push to `main`, on pull requests, and on manual dispatch. It is read-only, cancels superseded pull-request runs, and uses the runner's Python 3. A local composite action (`.github/actions/toolchain`) checks out the public platform and brand repositories at full commit SHAs with `persist-credentials: false`, then sets up Go from the pinned platform's `go.mod`. The workflow then runs `make validate`, which expands the same `GATE_TARGETS` list used locally:

- `cmd/genstatus -check` through `scripts/check_generated.py`. The script reverses only the site layer in a temporary checkout, then lets the platform generator compare the brand-resolved markup, `brand.manifest.json`, and every published brand asset. `scripts/build_site.py --check` separately reproduces the final page byte for byte.
- `cmd/brandlint` against the platform, brand, and status checkouts. It rejects raw colours, literal font stacks, external stylesheet imports, missing shell markers, unresolved placeholders, digest or size drift, and a published asset that a page does not reference.
- `cmd/statuscheck` loads the committed `status.json` through the platform's public status package and rejects a document that does not match the schema.
- The published brand assets match the SHA-256 digests and byte sizes in `brand.manifest.json`; exactly one `brand.<hash>.css` is linked, it is the manifest entry, and its digest matches. A second or older brand sheet fails.
- `index.html` and `404.html` share one CSP from `templates/csp.txt`; neither carries `frame-ancestors` in a meta policy.
- The static snapshot is re-rendered from the exact `status.json` bytes and compared with the committed HTML: digest, snapshot instant, headline, summary, stale notice, component rows, incident rows, counts, and times. A stale document may not show confirmed rows or repeat the publisher summary.
- The print palette is regenerated from the brand light block and compared byte for byte; the `@media print` block exists, hides the reverse lockup, shows the print-safe mark, and body text and status tokens measure at least 4.5:1 on the print canvas and on white with backgrounds dropped.
- The site manifest's four hashed assets match their SHA-256 and byte size, and each copy matches its source file or the generated print palette; the pages reference the hashed names and the print stylesheet is print-only.
- `status.json` schema: version 1, valid statuses, unique ids, both languages, UTC `Z` timestamps, paired `generated_at`/`expires_at`, a lifetime of at most 15 minutes, no heartbeat more than 5 minutes in the future, and no healthy claim when `generated_at` is null.
- The presentation contract: the fetch notice has role `alert` and exactly one retry button, the stale notice has role `status`, the two notices cannot be visible together, each component row stays compact, and the vitals instrument declares all five status segments.
- The header mark is measured from the file the page references and the surface `.status-header` paints; recoloured fills, a changed surface, and a header-size override fail.
- Every incident has the required fields and `updated_at` is not before `started_at`.
- `CNAME` is exactly `status.ia.sbktechno.com` with a final newline.
- `index.html`, `styles.css`, `app.js`, and `status-model.js` exist and are non-empty.

`make validate` runs the document/site validator, the unit tests, `make brand-check`, `make render-check`, the retention check, the platform `statuscheck`, and `cmd/brandlint`. `scripts/ci_contract_test.py` parses the Makefile and both workflows: it fails if `make validate` stops expanding `GATE_TARGETS`, if a workflow grows an inline check, if the toolchain refs stop being full 40-hex commit SHAs, or if publish stops pruning and validating before its commit. The Python suite runs `scripts/status_model_test.mjs` and `scripts/snapshot_contract_test.mjs` through Node, so the live browser model and the publish-time Python snapshot agree on loading, fresh, stale, null, future, aged, expired, and failed-fetch states.

No third-party action is used beyond `actions/checkout` and `actions/setup-go`; the local composite action pins both.

## Security and privacy

- `index.html` and `404.html` carry the same strict CSP, generated once from `templates/csp.txt`: `default-src 'none'; style-src 'self'; script-src 'self'; font-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'`. JavaScript and CSS live in separate files, with no inline scripts or inline styles.
- The meta policy deliberately omits `frame-ancestors`; browsers ignore that directive in a meta CSP. Clickjacking protection belongs in a response header at the edge.
- There are no secrets, cookies, browser storage, analytics, service workers, beacons, or external assets. The `status.json` fetch uses `credentials: "omit"`.
- Everything published in this repository and in `status.json` is public. Never put private platform data, client data, tokens, or internal URLs in the status file.

### Deployment follow-up: response headers

GitHub Pages does not allow arbitrary response headers. The following headers can only be set by the future edge; they are recorded here so the limitation is explicit:

| Header | Value | Why it cannot be a meta tag |
| --- | --- | --- |
| `Content-Security-Policy` | the `templates/csp.txt` policy plus `frame-ancestors 'none'` | `frame-ancestors` is ignored in a meta policy. |
| `Cache-Control` (HTML) | `public, max-age=600, must-revalidate` | Meta cache directives are not honoured consistently; Pages owns the response. |
| `Cache-Control` (hashed assets) | `public, max-age=31536000, immutable` | Requires a response header; the hashed URL already prevents mismatches. |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | Header-only. |
| `X-Content-Type-Options` | `nosniff` | Header-only. |
| `Referrer-Policy` | `no-referrer` | The meta tag is present, but the header is authoritative. |
| `X-Frame-Options` | `DENY` | Legacy complement to `frame-ancestors`. |

Until the edge exists, the hashed asset URLs and the single generated CSP are the protections this repository can enforce.
